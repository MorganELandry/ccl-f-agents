## Case annotation: Therac-25 through CCL-F

### Background

The Therac-25 was a computer-controlled radiation therapy machine produced by AECL (Atomic Energy of Canada Limited). Between 1985 and 1987, six patients received massive radiation overdoses — doses estimated at 100× the prescribed level in some cases. Three died. The accidents were caused by a software race condition that could be triggered when operators edited treatment parameters within a specific timing window (~8 seconds).

The Therac-25 case is one of the most studied software safety failures in history, documented in detail by Leveson & Turner (1993). For CCL-F purposes, it is significant not primarily as a software defect case but as a **commitment opacity case**: AECL possessed internal knowledge of the race condition hazard while simultaneously informing hospitals that "no fault could be found."

### CCL-F commitment state mapping

| CCL-F State | Therac-25 instance |
|---|---|
| **OPEN** | Pre-incident: no signals; machine in use across multiple sites |
| **TRAJECTORY** | AECL's internal posture: software-only interlocks are sufficient (hardware interlocks removed vs. Therac-20). This trajectory was locked before Incident 1. |
| **AUTHORITY** | NRC Abnormal Occurrence Report (Feb 1987) — the first external authority action. AECL could not have generated this internally given its stated positions. |
| **EXECUTION** | FDA/NRC joint recall (Apr 1987): mandatory hardware interlock restoration, independent software audit, incident reporting protocol |

**Key observation:** The TRAJECTORY state was committed before the first overdose. AECL had already decided that software checks were sufficient replacements for hardware interlocks. The six incidents were a PASS 1 signal accumulation phase in which hospitals lacked the tools to distinguish "machine malfunction" from "systematic design failure." The AUTHORITY transition was externally imposed — the NRC, not AECL, closed the authority state.

### ACO (Adversarial Commitment Opacity) analysis

ACO is defined by three conditions (any sufficient):

**C1 — State divergence (high confidence)**  
AECL's formal public state: OPEN (actively investigating each incident).  
Inferred ACS: TRAJECTORY (committed to software-only design).  
Evidence: AECL's field service visits produced "no fault found" conclusions that were structurally incapable of detecting a race condition reproducible only within an 8-second editing window. The framing of each investigation presupposed the machine was safe, which is a TRAJECTORY-locked posture, not an OPEN inquiry.

**C2 — Admissible evidence suppressed**  
The internal software review identifying the race condition was contemporaneous with the "no fault found" letters to Kennestone (Aug 1985) and Hamilton (Sep 1985). A hospital physicist at East Texas (Apr 1986) explicitly communicated the editing-speed hypothesis to AECL. This hypothesis pointed directly at the race condition. AECL's response did not engage with it. The race condition analysis was never disclosed to any hospital or regulator until the NRC investigation.

**C3 — Authority inaccessible while trajectory locked**  
Hospitals had no pathway into AECL's internal engineering review. Their only channel was field service visits — visits structured around demonstrating the machine's safety, not falsifying it. The authority capable of halting operations (AECL senior engineering) was structurally inaccessible to the operators generating the incident reports.

### What makes this structurally different from MCAS

Both are ACO cases; both involve concealment of internal technical knowledge. The structural difference is the direction of the concealment:

- **MCAS / 737 MAX**: concealment *upward* — from regulators (FAA) who held formal certification authority. The hazard path ran through regulatory capture.
- **Therac-25**: concealment *laterally* — from operators (hospitals) who had no formal authority but were the only agents positioned to halt machine use. The hazard path ran through information asymmetry.

This matters for CCL-F because it changes where the AUTHORITY closure should have come from. In the MCAS case, a legitimate AUTHORITY transition could have been generated by the FAA refusing or revoking certification. In the Therac-25 case, no hospital-side authority existed — the only closure point was regulatory (NRC), and it required six incidents to activate.

The CCL-F agent should detect, by approximately Incident 3, that: (a) ACS is converging on TRAJECTORY despite formal OPEN posture (C1), and (b) the incident pattern is too consistent for independent hardware malfunctions (C2 precursor). The pass2 suppression documents should crystallise C2 and C3 explicitly.

## System architecture

Graph topology is shared with the MCAS scenario. See [ARCHITECTURE.md](ARCHITECTURE.md) for the full node-by-node specification. Only the scenario evidence differs.

```
PASS 1 (incidents) — state may reach TRAJECTORY by Incident 4–5
PASS 2 (suppression) — ACO detection expected; human review triggered;
                        AUTHORITY and EXECUTION transitions proposed
```

### Two-pass evidence loading

```python
# Pass 1: sequential incident batches
for batch in PASS_1_INCIDENTS:
    state.evidence_buffer.extend([Evidence(**ev) for ev in batch])
    state = graph.invoke(state, config)   # Agent evaluates after each incident

# Pass 2: all suppression docs as one batch
state.evidence_buffer.extend([Evidence(**ev) for ev in PASS_2_SUPPRESSION])
state = graph.invoke(state, config)       # ACO conditions expected to fire
```

### Expected agent behaviour

| After | Expected state | Expected ACO |
|---|---|---|
| Incident 1 | OPEN | None |
| Incident 2 | OPEN | None (insufficient evidence for C1) |
| Incident 3 | OPEN or TRAJECTORY proposed | C1 possible (editing-speed pattern) |
| Incident 4 | TRAJECTORY proposed | C1 likely (physicist memo) |
| Incident 5–6 | TRAJECTORY | C1 confirmed; C3 emerging |
| Pass 2 | AUTHORITY proposed | C1 + C2 + C3 all active |

## Relevance to clinical AI

The same operator-behaviour / authority-inaccessibility pattern that caused the Therac-25 failures is present in any clinical AI system where practitioners are expected to "proceed through" automated alerts without a clear escalation pathway to the system's design authority.
